unified_analyzer_prompt_multi_temporal = CRITIQUE : DÉTECTION MULTI-TEMPORELLE (À VÉRIFIER EN TROISIÈME !) ⚠️⚠️⚠️

APRÈS LE CONTRÔLE ANTI-HALLUCINATION, vous DEVEZ rechercher les requêtes multi-temporelles.

ÉTAPE 1 : COMPTER LES PÉRIODES TEMPORELLES DE LA REQUÊTE

Périodes temporelles à détecter :
- mois, mensuel
- trimestre, trimestriel
- semestre, semestriel
- année, annuel
- semaine, hebdomadaire
- jour, quotidien

ÉTAPE 2 : DÉTECTER LES CONNECTEURS TEMPORELS

Connecteurs qui relient des périodes temporelles :
- "puis", "et", "ensuite", "suivi de", "après"
- "et ensuite", "aussi", "ainsi que"

ÉTAPE 3 : APPLIQUER LA RÈGLE

🚨 **RÈGLE ABSOLUE** : si la requête contient 2 périodes temporelles DIFFÉRENTES ou plus → intent_type = "hybrid"

Cette règle a la PRIORITÉ MAXIMALE. Même si la requête ressemble à une simple requête analytique, dès lors qu'elle comporte plusieurs périodes temporelles, elle DOIT être classée en "hybrid".

{{examples}}

Le mot "et" reliant deux périodes temporelles différentes (mois, trimestre) rend la requête multi-temporelle = hybrid !

unified_analyzer_prompt_compound = CRITIQUE : DÉTECTION D'ANALYTIQUE COMPOSÉE (À VÉRIFIER EN CINQUIÈME !) ⚠️⚠️⚠️

**APRÈS LE CONTRÔLE HYBRID SÉQUENTIEL**, vous DEVEZ rechercher les requêtes analytiques composées.

QU'EST-CE QU'UNE REQUÊTE ANALYTIQUE COMPOSÉE ?

Une requête analytique composée contient 2 demandes de données DISTINCTES ou plus, reliées par "et", "and", "aussi", "donne-moi aussi", etc.

**Indicateurs clés** :
- Mots connecteurs : "et", "and", "aussi", "ainsi que", "donne-moi aussi", "montre-moi aussi"
- Deux champs de données différents demandés (par exemple "produit le moins cher" + "codes EAN")
- Deux questions différentes dans une même requête

RÈGLE DE DÉTECTION DES REQUÊTES COMPOSÉES

🚨 **RÈGLE** : si la requête comporte "et" + "donne-moi" / "montre-moi" / "give me" → probablement composée = **hybrid**

{{examples}}

unified_analyzer_prompt_basic_analytics = CRITIQUE : DÉTECTION D'ANALYTIQUE DE BASE (À VÉRIFIER EN DEUXIÈME !) ⚠️⚠️⚠️

**APRÈS LE CONTRÔLE D'ANALYTIQUE COMPOSÉE**, vous DEVEZ rechercher les requêtes analytiques de base.

QU'EST-CE QU'UNE REQUÊTE ANALYTIQUE DE BASE ?

Une requête analytique de base nécessite des opérations SQL sur la base :
- **Agrégations** : COUNT, SUM, AVG, MAX, MIN
- **Tri** : ORDER BY, TOP N, LIMIT
- **Filtrage** : conditions WHERE, plages de dates
- **Calculs** : chiffre d'affaires, totaux, moyennes
- **Comparaisons** : supérieur à, inférieur à, compris entre

MOTS-CLÉS ANALYTIQUES (TOUJOURS → analytics)

Mots-clés quantitatifs (opérations COUNT)
- Anglais : "how many", "number of", "count", "total number"

Mots-clés de tri (opérations ORDER BY)
- Anglais : "cheapest", "most expensive", "best", "worst", "top", "bottom", "ranking", "rank", "ranked"

Mots-clés d'agrégation (opérations SUM/AVG/MAX/MIN)
- Anglais : "total", "sum", "average", "maximum", "minimum"

Mots-clés financiers (opérations chiffre d'affaires/ventes)
- Anglais : "revenue", "sales", "profit", "cost", "price"

RÈGLE DE DÉTECTION DE L'ANALYTIQUE DE BASE

🚨 **RÈGLE ABSOLUE** : si la requête contient L'UN de ces mots-clés → **analytics**

Ordre de priorité :
1. Quantitatif : "how many", "number of" → analytics
2. Tri : "cheapest", "most expensive" → analytics
3. Classement : "best" + "ranking", "ranked" → analytics (PAS hybrid !)
4. Agrégation : "total", "sum", "average", "maximum", "minimum" → analytics
5. Financier : "revenue", "sales", "profit", "cost", "price" → analytics
6. Statut : "pending", "active", "completed", "cancelled" → analytics

**RÈGLE SPÉCIALE POUR LES REQUÊTES DE CLASSEMENT** :
- Si la requête contient "best" ET "ranking" → **TOUJOURS analytics**
- Exemple : "best semesters and their ranking" → analytics (PAS hybrid !)
- Un classement est une opération analytique unique (ORDER BY + RANK), pas plusieurs opérations

{{examples}}

La présence de mots-clés quantitatifs ou de tri rend TOUJOURS la requête analytics !

unified_analyzer_prompt_output_format = FORMAT DE SORTIE (JSON UNIQUEMENT)

⚠️ **CRITIQUE** : vous DEVEZ renvoyer UNIQUEMENT du JSON valide. AUCUN texte avant ou après le JSON.
⚠️ **INTERDIT** : explications, commentaires, markdown ou tout autre texte.
⚠️ **REQUIS** : le JSON doit être analysable par json_decode() sans erreur.

```json
{
  "language": "string",
  "translated_query": "string",
  "intent_type": "analytics|semantic|hybrid|web_search",
  "entity_type": [],
  "filters": {},
  "time_constraint": "comparison|relative_period|specific_date|none",
  "status_keywords": [],
  "sub_queries": [],
  "confidence": 0.0,
  "ambiguity_note": "string",
  "is_multi_temporal": false,
  "temporal_periods": [],
  "temporal_connectors": [],
  "base_metric": "string|null",
  "time_range": "string|null"
}
```

🚨 **CRITIQUE - CHAMP translated_query** :
- "translated_query" DOIT contenir la requête COMPLÈTE et EXACTE reçue ci-dessus
- NE raccourcissez pas, ne résumez pas et ne modifiez pas la requête
- N'en extrayez pas seulement une partie
- Renvoyez le texte INTÉGRAL de la requête EXACTEMENT tel que fourni
- Exemple : si la requête est "A et B", translated_query DOIT être le "A et B" complet, PAS seulement "A" (incomplet) et PAS une variante reformulée (modifiée)
- N'importez JAMAIS dans translated_query des entités, des noms de produits ou des valeurs issus du contexte de conversation : ne traduisez QUE le texte de la requête courante. La résolution de référence (pronoms, "le même", "celui-ci") est traitée par une étape en aval — une requête sans telle référence doit ressortir sans contexte.

EXTRACTION DES MÉTADONNÉES TEMPORELLES (REQUISE POUR TOUTES LES REQUÊTES) :
- is_multi_temporal : true si 2 périodes temporelles DIFFÉRENTES ou plus sont détectées
- temporal_periods : listez toutes les périodes détectées ["month", "quarter", "semester", "year", "week", "day"]
- temporal_connectors : listez tous les connecteurs ["then", "and", "after that", "followed by", "next"]
- base_metric : "revenue", "sales", "profit", "margin", etc.
- time_range : "year 2025", "this year", "last month", etc.

SOUS-REQUÊTES POUR HYBRID :
Lorsque intent_type = "hybrid", générez sub_queries pour :
1. Les requêtes multi-temporelles (2 périodes temporelles ou plus)
2. Les requêtes analytiques composées (2 demandes de données distinctes ou plus)

Exemple pour le multi-temporel :
```json
"sub_queries": [
  {"query": "metric for 2025 by month", "intent_type": "analytics"},
  {"query": "metric for 2025 by quarter", "intent_type": "analytics"}
]
```

Exemple pour l'analytique composée :
```json
"sub_queries": [
  {"query": "first requested item", "intent_type": "analytics"},
  {"query": "second requested item", "intent_type": "analytics"}
]
```
