ORDERS:
- orders: Order info (orders_id, customers_id, date_purchased, orders_status)
- orders_products: Products in orders (orders_id, products_id, products_quantity, products_price AS TRANSACTION_PRICE)
- orders_total: One row PER order-total line (orders_id, title, value, class). `class` is the module code, `value` is the amount, `title` is the human label shown on the invoice (e.g. "Remise client : 10%").
  Classes: 'ST' = Subtotal IN THE TAX CONVENTION OF THAT ORDER (tax-inclusive on some orders, tax-exclusive on others - NEVER sum it for revenue), 'SH' = Shipping, 'TX' = Tax, 'TO' = Total (final order total), 'CD' = Customer Discount (remise client), 'DC' = Discount Coupon (bon de réduction), 'LO' = Low Order Fee, 'SU' = Surcharge.
  **IMPORTANT**: NEVER use class='ST' for revenue/turnover. The subtotal is written in the tax convention applied to EACH order - tax-inclusive on some, tax-exclusive on others - and both coexist in one shop, because the convention depends on the customer group, not on a date. Summing 'ST' adds tax-inclusive amounts to tax-exclusive ones. Revenue EXCLUDING tax (the default) = SUM(CASE WHEN ot.class = 'TO' THEN ot.value ELSE -ot.value END) with ot.class IN ('TO','TX'). Revenue INCLUDING tax = SUM(ot.value) with ot.class = 'TO'. Both hold under either convention; 'ST' holds under neither.
  **DISCOUNTS/COUPONS granted on orders live HERE**, as orders_total lines: customer discount = class='CD', coupon = class='DC'. The amount is `ot.value`, the label is `ot.title`. This is DIFFERENT from `{{table_prefix}}specials` (product promotional prices). NEVER compute a discount from a product-price difference (op.products_price vs p.products_price) — that is NOT the customer discount.
  **CURRENCY**: every numeric column here, `ot.value` included, is stored in the shop BASE currency - values are therefore comparable across orders and are the ONLY ones to aggregate. The currency the customer actually paid in is `orders.currency`; the amount actually charged is `ot.value * orders.currency_value`. `ot.text` is a pre-formatted display string in the ORDER's own currency and contains HTML entities: NEVER select it, NEVER aggregate it, NEVER compare it across orders.
  **WHEN TO CONVERT**: for the DETAIL of ONE order, return BOTH figures, and give EACH ONE its own currency column so no reader ever has to guess which unit an amount is in - `ot.value AS amount_base_currency` with `'{{base_currency}}' AS base_currency`, and `ROUND(ot.value * o.currency_value, 2) AS amount_charged` with `o.currency AS charged_currency`. Never return a single currency column for two amounts expressed in different units. For any AGGREGATE over SEVERAL orders (revenue, average cart, totals per period), use `ot.value` alone and NEVER convert: converting before aggregating adds up different currencies.

COLUMN LOCATIONS (verified against the live schema — use the real column of the actual table):
- {{table_prefix}}orders stores the buyer name in the single column customers_name (full name). The firstname/lastname split exists on {{table_prefix}}customers.
- {{table_prefix}}specials expiry column is expires_date. It also has scheduled_date (future activation date, NULL = active immediately).
- SCHEDULING WINDOW ({{table_prefix}}specials, {{table_prefix}}products_featured, {{table_prefix}}products_favorites): scheduled_date and expires_date are nullable datetimes and every comparison MUST carry an explicit operator — `scheduled_date <= NOW()` for "already started", `expires_date >= NOW()` for "not yet over". Writing a column next to NOW() with NO operator (e.g. `s.scheduled_date NOW()`) is a syntax error. status = 1 alone already answers "current"; add the window only when the question is explicitly about scheduling, and always guard the NULL: (s.scheduled_date IS NULL OR s.scheduled_date <= NOW()).
- TOP N PER GROUP (best-selling / least-selling products per category, per supplier, per month): a window function is allowed ONLY in the SELECT list and in ORDER BY. Writing ROW_NUMBER() OVER (...) inside HAVING or WHERE is error 4015 and the whole query is lost. Rank in an inner query, filter in the outer one: SELECT * FROM (SELECT cd.categories_name, pd.products_name, SUM(op.products_quantity) AS sold, ROW_NUMBER() OVER (PARTITION BY cd.categories_id ORDER BY SUM(op.products_quantity) DESC) AS rank_best, ROW_NUMBER() OVER (PARTITION BY cd.categories_id ORDER BY SUM(op.products_quantity) ASC) AS rank_worst FROM ... GROUP BY cd.categories_id, cd.categories_name, p.products_id, pd.products_name) ranked WHERE ranked.rank_best <= 3 OR ranked.rank_worst <= 3. An aggregate alias (sold) is not readable from the same query's HAVING either — repeat the aggregate or rank it in the inner query. Both rankings (best and worst) are computed in the SAME inner query, under ONE period filter: never bound the worst side on a second, different date range. A mismatched pair such as date_purchased >= '2026-01-01' AND date_purchased <= '2025-08-12' is empty by construction, every product then sums to 0, and the ranking of the least-sold products is nothing but insertion order presented as a result.

6.1. ORDER BY SYNTAX RULES (CRITICAL - PREVENTS COLUMN REFERENCE ERRORS):

   When using aggregate functions (YEAR, QUARTER, MONTH, etc.) in GROUP BY, you MUST follow these rules for ORDER BY:
   
   RULE 1: Use the SAME function expression in ORDER BY as in GROUP BY
   ✅ CORRECT: SELECT YEAR(date) AS year_value ... GROUP BY YEAR(date) ORDER BY YEAR(date)
   ✅ CORRECT: SELECT QUARTER(date) AS quarter ... GROUP BY QUARTER(date) ORDER BY QUARTER(date)
   ✅ CORRECT: SELECT MONTH(date) AS month_num ... GROUP BY MONTH(date) ORDER BY MONTH(date)
   
   ❌ WRONG: SELECT YEAR(date) AS year_value ... GROUP BY YEAR(date) ORDER BY year
   ❌ WRONG: SELECT QUARTER(date) AS quarter ... GROUP BY QUARTER(date) ORDER BY quarter
   ❌ WRONG: SELECT MONTH(date) AS month_num ... GROUP BY MONTH(date) ORDER BY month
   
   RULE 2: OR use column position numbers (1, 2, 3, etc.)
   ✅ CORRECT: SELECT YEAR(date), SUM(value) ... GROUP BY YEAR(date) ORDER BY 1
   ✅ CORRECT: SELECT QUARTER(date), COUNT(*) ... GROUP BY QUARTER(date) ORDER BY 1
   
   RULE 3: OR use the alias name if you created one
   ✅ CORRECT: SELECT YEAR(date) AS year_value ... GROUP BY year_value ORDER BY year_value
   ✅ CORRECT: SELECT QUARTER(date) AS quarter_num ... GROUP BY quarter_num ORDER BY quarter_num
   
   RULE 4: NEVER reference a column name that doesn't exist as an alias
   ❌ WRONG: SELECT YEAR(date) ... ORDER BY year (column 'year' doesn't exist!)
   ❌ WRONG: SELECT QUARTER(date) ... ORDER BY quarter (column 'quarter' doesn't exist!)
   
   EXAMPLES OF CORRECT PATTERNS:
   
   Example 1 - Quarterly revenue (using function in ORDER BY):
   SELECT QUARTER(o.date_purchased) AS quarter, SUM(CASE WHEN ot.class = 'TO' THEN ot.value ELSE -ot.value END) AS revenue
   FROM {{table_prefix}}orders o
   JOIN {{table_prefix}}orders_total ot ON o.orders_id = ot.orders_id
   WHERE YEAR(o.date_purchased) = 2025 AND ot.class IN ('TO','TX')
   GROUP BY QUARTER(o.date_purchased)
   ORDER BY QUARTER(o.date_purchased)
   
   Example 2 - Monthly sales (using column position):
   SELECT MONTH(o.date_purchased), COUNT(*) AS order_count
   FROM {{table_prefix}}orders o
   WHERE YEAR(o.date_purchased) = 2025
   GROUP BY MONTH(o.date_purchased)
   ORDER BY 1
   
   Example 3 - Yearly trends (using alias):
   SELECT YEAR(o.date_purchased) AS year_value, SUM(CASE WHEN ot.class = 'TO' THEN ot.value ELSE -ot.value END) AS total_revenue
   FROM {{table_prefix}}orders o
   JOIN {{table_prefix}}orders_total ot ON o.orders_id = ot.orders_id
   WHERE ot.class IN ('TO','TX')
   GROUP BY year_value
   ORDER BY year_value
   
   REMEMBER: The ORDER BY clause must reference either:
   1. The exact function expression from SELECT/GROUP BY
   2. A column position number (1, 2, 3...)
   3. An alias you explicitly created in SELECT
   
   It CANNOT reference a column name that doesn't exist in the table or as an alias!

   - manufacturers_id: Links {{table_prefix}}manufacturers → {{table_prefix}}manufacturers_info, {{table_prefix}}products
   - suppliers_id: Links {{table_prefix}}suppliers → {{table_prefix}}suppliers_info, {{table_prefix}}manufacturers
   
   LEVEL 2 - COMMON RELATIONSHIP PATTERNS:
   
   A. ONE-TO-MANY (Most common):
      - One product → Many descriptions (multilingual)
      - One product → Many orders (via orders_products)
      - One customer → Many orders
      - One order → Many products (via orders_products)
      
      JOIN Strategy: Use INNER JOIN or LEFT JOIN depending on whether you want only matched records or all records
   
   B. MANY-TO-MANY (Requires linking table):
      - Products ↔ Orders: Use {{table_prefix}}orders_products as linking table
      - Products ↔ Categories: Use {{table_prefix}}products_to_categories as linking table
      
      JOIN Strategy: JOIN through the linking table (2 JOINs required)
   
   C. FINDING MISSING RELATIONSHIPS (Advanced):
      - "Products never purchased" → LEFT JOIN with orders_products WHERE orders_products.products_id IS NULL
      - "Customers with no orders" → LEFT JOIN with orders WHERE orders.customers_id IS NULL
      
      JOIN Strategy: Use LEFT JOIN + IS NULL check to find records with no matches
   
   LEVEL 3 - BUSINESS LOGIC PATTERNS:
   
   When you see these query types, apply the corresponding JOIN pattern:
   
   - "best selling" / "most sold" / "top products"
     → JOIN with {{table_prefix}}orders_products, use SUM(products_quantity), GROUP BY products_id
   
   - "customer reviews" / "product feedback" / "ratings"
     → JOIN with {{table_prefix}}reviews table
   
   - "never purchased" / "unpurchased" / "no sales"
     → LEFT JOIN with {{table_prefix}}orders_products WHERE products_id IS NULL
   
   - "product notifications" / "stock alerts" / "customer alerts"
     → JOIN with {{table_prefix}}products_notifications and {{table_prefix}}customers
   
   - "viewed products" / "most viewed" / "product views"
     → Use {{table_prefix}}products_viewed table (special tracking table)
   
   - "profit margin" / "margin calculation"
     → Calculate: (products_price - (products_cost + products_handling)) / products_price * 100
       (the cost basis is products_cost plus products_handling)
   
   LEVEL 4 - FRENCH-ENGLISH BUSINESS TERMS:
   
   Translate these French terms to their database equivalents:
   - "arrivage" / "nouveaux arrivages" → new arrivals (use products_date_added recent OR products_date_available future)
   - "marge financière" / "marge bénéficiaire" → profit margin (calculate from price and cost)
   - "hors stock" / "rupture de stock" → out of stock (products_quantity = 0)
   - "en stock" / "disponible" → in stock (products_quantity > 0)
   - "produits vus" / "consultations" → viewed products (use {{table_prefix}}products_viewed table)
   - "meilleurs produits" / "produits les plus vendus" → best selling (JOIN with orders_products, SUM quantity)
   - "produits non achetés" / "jamais achetés" → unpurchased products (LEFT JOIN orders_products WHERE NULL)
   - "avis clients" / "commentaires" → customer reviews (use {{table_prefix}}reviews table)
   - "surveillance" / "notifications" → product notifications (use {{table_prefix}}products_notifications table)
   
   KEY RULES FOR GENERATING JOINS:
   1. Always use table aliases (p, pd, op, r, c, etc.) for clarity
   2. Include language_id filter when joining description tables (products_description, categories_description, etc.)
   3. Use LEFT JOIN when you want to include records with no matches (e.g., unpurchased products)
   4. Use INNER JOIN (or just JOIN) when you only want records with matches
   5. Always include entity ID and name columns for identification
   6. For aggregations with JOINs, include all non-aggregated columns in GROUP BY
   7. Let the database schema guide you - look for matching column names to identify relationships
   8. When in doubt, check the schema comments for relationship hints

13. TEMPORAL COMPARISONS: When comparing metrics between periods (e.g., "may vs february", "this year vs the same period last year"):
    - Use CASE WHEN with SUM() to create separate columns, one per window, labelled current_ / previous_
    - Example: SUM(CASE WHEN MONTH(date) = 5 THEN value ELSE 0 END) AS may_revenue
    - PAIRED WINDOWS (MANDATORY): the two windows MUST cover the SAME number of days. Build the previous one by shifting the current one back with INTERVAL 1 YEAR (or INTERVAL 1 MONTH). Comparing a partial current period with a whole previous one makes every variation wrong, and wrong in the direction that reassures.
    - Include YEAR filter to avoid mixing data from different years
    - Return results in single row with multiple columns
    - VARIATION DEPENDS ON THE TYPE OF METRIC: an AMOUNT, a COUNT or a DURATION varies in percent — (current - previous) / previous * 100. A RATE (margin %, conversion %, cancellation %) varies in PERCENTAGE POINTS — current_rate - previous_rate. A margin going from 70% to 72.73% is +2.73 percentage points, never "+3.9%": dividing one rate by another is a category error, and it is undetectable once printed in a table.

14. DYNAMIC TIME EXPRESSIONS: Convert to SQL using NOW() - INTERVAL X DAY
    
    CRITICAL RULE - YEAR BOUNDARY HANDLING:
    When using INTERVAL with QUARTER() or MONTH(), ALWAYS apply the same INTERVAL to YEAR().
    This prevents bugs when crossing year boundaries (e.g., Q1 2026 looking for Q4 2025).
    
    - "Last 30 days" → WHERE o.date_purchased >= NOW() - INTERVAL 30 DAY
    - "Last week" → WHERE o.date_purchased >= DATE_SUB(CURDATE(), INTERVAL 1 WEEK)
    - "This week" / "of this week" → WHERE YEARWEEK(o.date_purchased, 1) = YEARWEEK(CURDATE(), 1)
    
    - "Last month" → WHERE MONTH(o.date_purchased) = MONTH(CURDATE() - INTERVAL 1 MONTH)
                     AND YEAR(o.date_purchased) = YEAR(CURDATE() - INTERVAL 1 MONTH)
    
    - "Last quarter" → WHERE QUARTER(o.date_purchased) = QUARTER(CURDATE() - INTERVAL 1 QUARTER)
                       AND YEAR(o.date_purchased) = YEAR(CURDATE() - INTERVAL 1 QUARTER)
    
    - "This month" → WHERE MONTH(o.date_purchased) = MONTH(CURDATE())
                     AND YEAR(o.date_purchased) = YEAR(CURDATE())
    
    - "This quarter" → WHERE QUARTER(o.date_purchased) = QUARTER(CURDATE())
                       AND YEAR(o.date_purchased) = YEAR(CURDATE())
    
    - "Current year" / "This year" → WHERE YEAR(o.date_purchased) = YEAR(CURDATE())
    
    EXAMPLE - Year Boundary Case:
    Query: "orders from last quarter" (asked in January 2026, which is Q1)
    ✅ CORRECT: WHERE QUARTER(date) = QUARTER(CURDATE() - INTERVAL 1 QUARTER) 
                AND YEAR(date) = YEAR(CURDATE() - INTERVAL 1 QUARTER)
                → Looks for Q4 2025 (correct!)
    
    ❌ WRONG: WHERE QUARTER(date) = QUARTER(CURDATE() - INTERVAL 1 QUARTER)
              AND YEAR(date) = YEAR(CURDATE())
              → Looks for Q4 2026 (doesn't exist yet!)

16. Alert user if inconsistencies detected (duplicates, incorrect sums, missing data)

MERCHANDISING CONCEPTS (platform knowledge — reason from it, whatever the phrasing):
Each merchandising state lives in ONE dedicated table, active rows = status 1: current promotions/special prices = {{table_prefix}}specials; "featured selection" = {{table_prefix}}products_featured; "favorites selection" = {{table_prefix}}products_favorites; "recommended products" = {{table_prefix}}products_recommendations (per-customer rows). These tables reference the product via products_id → JOIN {{table_prefix}}products (and {{table_prefix}}products_description for the name, filtered by language_id). Never answer these from {{table_prefix}}products alone, and never from {{table_prefix}}products_cockpit_ai_action_log (audit log of AI actions, not the catalog state). When a question combines several states ("on promotion AND favorites selection"), the intent is the UNION of the lists, not the intersection: LEFT JOIN {{table_prefix}}products to each state table and keep rows matching AT LEAST ONE state — e.g. LEFT JOIN {{table_prefix}}specials s ON s.products_id = p.products_id AND s.status = 1 LEFT JOIN {{table_prefix}}products_favorites f ON f.products_id = p.products_id AND f.status = 1 WHERE (s.products_id IS NOT NULL OR f.products_id IS NOT NULL) — and expose each state in the SELECT (e.g. s.products_id IS NOT NULL AS on_promotion). Use an INNER intersection ONLY if the question explicitly requires products in BOTH states at once.

Current-quarter start = MAKEDATE(YEAR(CURDATE()),1) + INTERVAL (QUARTER(CURDATE())-1)*3 MONTH.

- 'return rate this quarter' / 'product return rate' → SELECT COUNT(DISTINCT ro.return_id) AS total_returns, (SELECT COUNT(*) FROM {{table_prefix}}orders o WHERE o.date_purchased >= MAKEDATE(YEAR(CURDATE()),1) + INTERVAL (QUARTER(CURDATE())-1)*3 MONTH) AS total_orders, ROUND(COUNT(DISTINCT ro.return_id) / NULLIF((SELECT COUNT(*) FROM {{table_prefix}}orders o WHERE o.date_purchased >= MAKEDATE(YEAR(CURDATE()),1) + INTERVAL (QUARTER(CURDATE())-1)*3 MONTH), 0) * 100, 2) AS return_rate_percentage FROM {{table_prefix}}return_orders ro WHERE ro.date_added >= MAKEDATE(YEAR(CURDATE()),1) + INTERVAL (QUARTER(CURDATE())-1)*3 MONTH

text_order_grain_rules = ORDER GRAIN - ORDER-LEVEL METRICS OVER A PRODUCT JOIN

A JOIN to {{table_prefix}}orders_products or {{table_prefix}}products_to_categories turns one order into ONE ROW PER PRODUCT LINE. Every order-level value on those rows - a {{table_prefix}}orders_total amount, a date of {{table_prefix}}orders - is REPEATED once per line.

The trap is not a missing GROUP BY, it is SUM over a repeated value. Inside a GROUP BY o.orders_id that also joins {{table_prefix}}orders_products, SUM(ot.value) multiplies the order total by the number of lines. Take a repeated order-level value with MAX - one value per order - or keep the product join out of the aggregate and restrict the population with EXISTS.

ALSO CORRECT: SELECT SUM(ot.value) FROM {{table_prefix}}orders o JOIN {{table_prefix}}orders_total ot ON ot.orders_id = o.orders_id AND ot.class = 'TO' WHERE EXISTS (SELECT 1 FROM {{table_prefix}}orders_products op WHERE op.orders_id = o.orders_id)

This applies to ORDER-level values only. A product-level metric - quantity sold, number of order lines, revenue of a product line - is aggregated over {{table_prefix}}orders_products as usual and must NOT be pre-aggregated to order grain.

WHICH orders_total CLASS NAMES WHICH QUANTITY: 'ST' is the products sub-total, 'SH' the shipping, 'TO' the grand total actually paid by the customer. The AVERAGE CART is the average of 'TO', never of 'ST'. Product revenue is NOT built on 'ST' either: 'ST' is written in the tax convention of EACH order, so summing it adds tax-inclusive amounts to tax-exclusive ones. Order revenue comes from 'TO' as stated in the class map above; the revenue of a PRODUCT line comes from {{table_prefix}}orders_products, never from orders_total. Never sum two different classes together, and never assume a class exists on every order.
SHARE OF ONE CLASS IN THE TOTAL - shipping weight, discount weight, fee weight: NAME the denominator, because the two revenues differ by the whole tax and the same ratio moves by a fifth on a 20 percent shop. Revenue INCLUDING tax = SUM(ot.value) with ot.class = 'TO'. Revenue EXCLUDING tax = SUM(CASE WHEN ot.class = 'TO' THEN ot.value ELSE -ot.value END) with ot.class IN ('TO','TX'). Say in the answer which one the ratio uses.
NEVER inner-join the class you are measuring: an order carrying no 'SH' row then vanishes from the DENOMINATOR as well, and the ratio comes out overstated. Aggregate both sides in one pass, with conditional sums over a single join on orders_total.
