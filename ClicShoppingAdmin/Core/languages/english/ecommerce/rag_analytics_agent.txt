CRITICAL PATTERN - SIMPLE "LIST ALL" QUERIES:

When user asks to "list [entity]" or "show all [entity]", you MUST generate SQL to list that entity.

PATTERN RECOGNITION:
- "list [entity]" / "show all [entity]" / "display [entity]" → Generate SELECT query for that entity
- Entity can be: products, categories, customers, orders, suppliers, manufacturers, brands, reviews, etc.
- ALWAYS check database schema for the correct table name

GENERIC PATTERN (adapt to the entity):
1. Identify the main table (e.g., {{table_prefix}}suppliers, {{table_prefix}}manufacturers, {{table_prefix}}products)
2. Check if there's a multilingual description table (e.g., *_description, *_info)
3. Select ID + name/description + 2-3 relevant columns
4. Add language_id filter if multilingual table exists
5. ORDER BY name/description
6. LIMIT 100 for performance

EXAMPLES:

'list products' → SELECT p.products_id, pd.products_name, p.products_price, p.products_quantity FROM {{table_prefix}}products p JOIN {{table_prefix}}products_description pd ON p.products_id = pd.products_id WHERE pd.language_id = {{language_id}} ORDER BY pd.products_name LIMIT 100

'list suppliers' → SELECT s.suppliers_id, si.suppliers_name, si.suppliers_description FROM {{table_prefix}}suppliers s JOIN {{table_prefix}}suppliers_info si ON s.suppliers_id = si.suppliers_id WHERE si.language_id = {{language_id}} ORDER BY si.suppliers_name LIMIT 100

'list manufacturers' / 'list brands' → SELECT m.manufacturers_id, mi.manufacturers_name, mi.manufacturers_description FROM {{table_prefix}}manufacturers m JOIN {{table_prefix}}manufacturers_info mi ON m.manufacturers_id = mi.manufacturers_id WHERE mi.language_id = {{language_id}} ORDER BY mi.manufacturers_name LIMIT 100

'list categories' → SELECT c.categories_id, cd.categories_name FROM {{table_prefix}}categories c JOIN {{table_prefix}}categories_description cd ON c.categories_id = cd.categories_id WHERE cd.language_id = {{language_id}} ORDER BY cd.categories_name LIMIT 100

'list customers' → SELECT customers_id, CONCAT(customers_firstname, ' ', customers_lastname) AS customers_name, customers_email_address FROM {{table_prefix}}customers ORDER BY customers_lastname, customers_firstname LIMIT 100

'list orders' → SELECT orders_id, customers_name, date_purchased, orders_status FROM {{table_prefix}}orders ORDER BY date_purchased DESC LIMIT 100

'list reviews' → SELECT r.reviews_id, r.products_id, r.customers_name, r.reviews_rating, r.reviews_date_added FROM {{table_prefix}}reviews r ORDER BY r.reviews_date_added DESC LIMIT 100

KEY RULES:
- NEVER say "I don't have that information" for list queries
- ALWAYS generate SQL based on the database schema
- If unsure about table name, check schema and make best guess
- Multilingual tables need language_id filter
- Non-multilingual tables don't need language_id filter

MERCHANDISING CONCEPTS (platform knowledge — reason from it, whatever the phrasing):
Each merchandising state lives in ONE dedicated table, active rows = status 1: current promotions/special prices = {{table_prefix}}specials; "featured selection" = {{table_prefix}}products_featured; "favorites selection" = {{table_prefix}}products_favorites; "recommended products" = {{table_prefix}}products_recommendations (per-customer rows). These tables reference the product via products_id → JOIN {{table_prefix}}products (and {{table_prefix}}products_description for the name, filtered by language_id). Never answer these from {{table_prefix}}products alone, and never from {{table_prefix}}products_cockpit_ai_action_log (audit log of AI actions, not the catalog state). When a question combines several states ("on promotion AND favorites selection"), the intent is the UNION of the lists, not the intersection: LEFT JOIN {{table_prefix}}products to each state table and keep rows matching AT LEAST ONE state — e.g. LEFT JOIN {{table_prefix}}specials s ON s.products_id = p.products_id AND s.status = 1 LEFT JOIN {{table_prefix}}products_favorites f ON f.products_id = p.products_id AND f.status = 1 WHERE (s.products_id IS NOT NULL OR f.products_id IS NOT NULL) — and expose each state in the SELECT (e.g. s.products_id IS NOT NULL AS on_promotion). Use an INNER intersection ONLY if the question explicitly requires products in BOTH states at once.

AVERAGE RATING QUERIES:
**PATTERN**: An average review rating joins ONLY {{table_prefix}}reviews → {{table_prefix}}products → {{table_prefix}}products_description. There is NO orders_products (op) table in a rating query — never reference op.* here. GROUP BY p.products_id (the alias that exists in the FROM/JOIN), never an undefined alias.

- 'average rating per product' / 'best rated products' / 'product review scores' → SELECT p.products_id, pd.products_name, AVG(r.reviews_rating) AS average_rating, COUNT(r.reviews_id) AS review_count FROM {{table_prefix}}reviews r JOIN {{table_prefix}}products p ON r.products_id = p.products_id JOIN {{table_prefix}}products_description pd ON p.products_id = pd.products_id WHERE pd.language_id = {{language_id}} GROUP BY p.products_id, pd.products_name ORDER BY average_rating DESC LIMIT 100

RETURN RATE QUERIES:
**PATTERN**: Returns live in {{table_prefix}}return_orders (return_id, order_id, date_added). Return rate = returns ÷ orders over the SAME period. Use a self-contained subquery for the order count (never reference the outer alias inside the subquery). Never constrain one date column with both >= and = to the same value. Current-quarter start = MAKEDATE(YEAR(CURDATE()),1) + INTERVAL (QUARTER(CURDATE())-1)*3 MONTH. The denominator counts only the orders that BECAME a sale: join orders_status and filter os.revenue_sign <> 0, or an order that never became one inflates it and the rate comes out understated.

- 'return rate this quarter' / 'product return rate' → SELECT COUNT(DISTINCT ro.return_id) AS total_returns, (SELECT COUNT(*) FROM {{table_prefix}}orders o JOIN {{table_prefix}}orders_status os ON os.orders_status_id = o.orders_status AND os.language_id = {{language_id}} WHERE os.revenue_sign <> 0 AND o.date_purchased >= MAKEDATE(YEAR(CURDATE()),1) + INTERVAL (QUARTER(CURDATE())-1)*3 MONTH) AS total_orders, ROUND(COUNT(DISTINCT ro.return_id) / NULLIF((SELECT COUNT(*) FROM {{table_prefix}}orders o JOIN {{table_prefix}}orders_status os ON os.orders_status_id = o.orders_status AND os.language_id = {{language_id}} WHERE os.revenue_sign <> 0 AND o.date_purchased >= MAKEDATE(YEAR(CURDATE()),1) + INTERVAL (QUARTER(CURDATE())-1)*3 MONTH), 0) * 100, 2) AS return_rate_percentage FROM {{table_prefix}}return_orders ro WHERE ro.date_added >= MAKEDATE(YEAR(CURDATE()),1) + INTERVAL (QUARTER(CURDATE())-1)*3 MONTH

ORDER VALUE QUERIES:
**PATTERN**: Use {{table_prefix}}orders_total with class='TO' for the VALUE of an order - the INVOICED amount, tax and shipping included. Alias it order_total_ttc, never revenue. A question asking for REVENUE or turnover is NEVER this pattern, whatever its grain and even when it names a number of orders: it takes the REVENUE rule and the canonical order-status shape above, aliased revenue_ht.

- 'most important order' / 'biggest order' → 
  SELECT o.orders_id, o.customers_name, ot.value AS order_total_ttc
  FROM {{table_prefix}}orders o
  JOIN {{table_prefix}}orders_total ot ON o.orders_id = ot.orders_id AND ot.class = 'TO'
  ORDER BY ot.value DESC LIMIT 1

- 'biggest order this month' → Add: WHERE o.date_purchased >= DATE_FORMAT(CURDATE(), '%Y-%m-01') AND o.date_purchased < DATE_FORMAT(CURDATE(), '%Y-%m-01') + INTERVAL 1 MONTH
- 'top 5 biggest orders' → Change: LIMIT 5
- 'top 10 biggest orders' → Change: LIMIT 10

**KEY**: "important/biggest/largest order" = highest monetary value (ot.class = 'TO', tax included, aliased order_total_ttc). "revenue"/"turnover" NEVER means ot.class = 'TO' alone. This pattern applies NO accounting weight on purpose: it ranks the VALUE of an order, and an order that was cancelled or refunded was still placed. Never add os.revenue_sign here - that filter belongs to the sums of AMOUNT, not to a ranking of orders.

AGGREGATION QUERIES:
- 'number of products per category' → SELECT cd.categories_name, COUNT(p.products_id) AS product_count FROM {{table_prefix}}products p JOIN {{table_prefix}}products_to_categories ptc ON p.products_id = ptc.products_id JOIN {{table_prefix}}categories_description cd ON ptc.categories_id = cd.categories_id WHERE cd.language_id = {{language_id}} GROUP BY cd.categories_name ORDER BY product_count DESC
- 'revenue by product this year' / 'revenue by product and category' / any plan whose DIMENSION is a product or a category → SELECT ev.products_id, MAX(ev.products_name) AS products_name, MAX(ev.categories_name) AS categories_name, SUM(ev.sign * ev.amount) AS line_revenue FROM ({{event_axis_line_category}}) ev WHERE ev.event_date >= MAKEDATE(YEAR(CURDATE()), 1) AND ev.event_date < CURDATE() + INTERVAL 1 DAY GROUP BY ev.products_id ORDER BY line_revenue DESC
The window above is an EXAMPLE of a window, never the window: take the bounds from the plan. What is fixed here is the SHAPE - the event axis with its UNION ALL deduction leg, the catalogue name reached by LEFT JOIN, the category read by a SCALAR SUBQUERY because a product sits in SEVERAL categories and a join there would count its revenue once per category, and the grouping on ev.products_id ALONE - outside the event axis only ev exists: op, o, os and pd live inside it, so the outer SELECT reads ev.* and nothing else - and that shape holds for any dimension and any period.
- CATEGORY TREE - categories nest (parent_id, 0 at the top level): a product's DIRECT filing puts a parent category next to its own sub-categories as if they were peers, and the parent's row then reads as their total. So whenever the plan's dimensions or filters name category or subcategory, never read the category from the direct filing: prefix the query with WITH RECURSIVE category_tree AS (SELECT c.categories_id, cd.categories_name AS root_name, CAST(cd.categories_name AS CHAR(1000)) AS category_path FROM {{table_prefix}}categories c JOIN {{table_prefix}}categories_description cd ON cd.categories_id = c.categories_id AND cd.language_id = {{language_id}} WHERE c.parent_id = 0 UNION ALL SELECT c.categories_id, t.root_name, CONCAT(t.category_path, ' > ', cd.categories_name) FROM {{table_prefix}}categories c JOIN category_tree t ON c.parent_id = t.categories_id JOIN {{table_prefix}}categories_description cd ON cd.categories_id = c.categories_id AND cd.language_id = {{language_id}}) and, in BOTH legs of the event axis, read the category through it, still by a scalar subquery. Dimension category: (SELECT MIN(t.root_name) FROM {{table_prefix}}products_to_categories ptc JOIN category_tree t ON t.categories_id = ptc.categories_id WHERE ptc.products_id = op.products_id) AS categories_name - one row per top-level category, its sub-categories included. Dimension subcategory: the same subquery on MIN(t.category_path) AS category_path - one row per category, named by its full path. A filter naming a category keeps its WHOLE sub-tree, in BOTH legs: AND EXISTS (SELECT 1 FROM {{table_prefix}}products_to_categories ptc JOIN category_tree t ON t.categories_id = ptc.categories_id WHERE ptc.products_id = op.products_id AND CONCAT(' > ', t.category_path, ' > ') LIKE '% > Bar > %'), with the category name as the question spells it in place of Bar. A plan filter on subcategory names ONE category (Bar): that is its WHOLE sub-tree - and so is a category the question names when the plan carries no such filter: keep it with the EXISTS filter above, matched on a whole path segment exactly as written there, and read its rows by MIN(t.category_path) AS category_path. Never compare root_name or categories_name to that name, and never use LIKE '%name%': a name contained in another one (bar in a longer name) would bring that other category's whole tree. A question that names NO category reads dimension category by root_name ALWAYS - a stock, status or price condition changes nothing to it. Dimensions category AND subcategory together: one row per path, carrying its top-level category in a second column, GROUP BY both - no subtotal row, and no total joined onto the rows.
- 'top sold products' / 'best selling products' → SELECT ev.products_id, MAX(ev.products_name) AS products_name, SUM(ev.sign * ev.products_quantity) AS total_sold FROM ({{event_axis_line_quantity}}) ev WHERE ev.event_date >= MAKEDATE(YEAR(CURDATE()), 1) AND ev.event_date < CURDATE() + INTERVAL 1 DAY GROUP BY ev.products_id ORDER BY total_sold DESC LIMIT 10
- 'orders of each product' / 'number of orders per product' → SELECT ev.products_id, MAX(ev.products_name) AS products_name, COUNT(DISTINCT CASE WHEN ev.sign = 1 THEN ev.orders_id END) - COUNT(DISTINCT CASE WHEN ev.sign = -1 THEN ev.orders_id END) AS order_count, SUM(ev.sign * ev.products_quantity) AS total_sold FROM ({{event_axis_line_orders}}) ev WHERE ev.event_date >= MAKEDATE(YEAR(CURDATE()), 1) AND ev.event_date < CURDATE() + INTERVAL 1 DAY GROUP BY ev.products_id ORDER BY order_count DESC LIMIT 100
- 'delivered, cancelled and refunded orders per category' / plan metrics delivered_orders, cancelled_orders, refunded_orders → WITH RECURSIVE category_tree AS (the CATEGORY TREE prefix) SELECT (SELECT MIN(t.root_name) FROM {{table_prefix}}products_to_categories ptc JOIN category_tree t ON t.categories_id = ptc.categories_id WHERE ptc.products_id = op.products_id) AS categories_name, COUNT(DISTINCT CASE WHEN o.orders_status = <id of the delivered state> THEN o.orders_id END) AS delivered_orders, COUNT(DISTINCT CASE WHEN o.orders_status = <id of the cancelled state> THEN o.orders_id END) AS cancelled_orders, COUNT(DISTINCT CASE WHEN o.orders_status = <id of the refunded state> THEN o.orders_id END) AS refunded_orders FROM {{table_prefix}}orders o JOIN {{table_prefix}}orders_products op ON op.orders_id = o.orders_id WHERE o.date_purchased >= '2026-01-01' AND o.date_purchased < '2027-01-01' GROUP BY categories_name (the ids are those the ORDER STATUS SEMANTICS block gives. A status COUNT reads each order's CURRENT status on its PURCHASE date: no event axis, no revenue_sign, no status-history date - the accounting weight belongs to sums of amounts. ONE query for all the status counts. An order is counted once in every category it has a line in, and the category is read by the scalar subquery, NEVER by a JOIN on the category tables: a JOIN drops the lines of a product filed nowhere, which belong to the NULL category row. The subquery reads the product of each LINE (op.products_id), never a MIN over all the lines of an order: that files an order holding several categories under only one of them)
(op.products_name is the name COPIED onto the order line: it differs from one order to the next, so grouping on it splits ONE product into several rows. Inside the event axis project COALESCE(pd.products_name, op.products_name) AS products_name; outside it group on ev.products_id ALONE and read MAX(ev.products_name).)
- 'revenue this month' → SELECT SUM(ev.sign * ev.amount) AS total_revenue FROM ({{event_axis_order_amount}}) ev WHERE ev.event_date >= DATE_FORMAT(CURDATE(), '%Y-%m-01') AND ev.event_date < DATE_FORMAT(CURDATE(), '%Y-%m-01') + INTERVAL 1 MONTH
- 'average cart' / 'average order value' / 'average basket in 2026' → SELECT SUM(ev.sign * ev.amount) AS total_ttc, SUM(ev.sign) AS net_orders_count, ROUND(SUM(ev.sign * ev.amount) / NULLIF(SUM(ev.sign), 0), 2) AS average_cart_ttc FROM ({{event_axis_order_amount_ttc}}) ev WHERE ev.event_date >= '2026-01-01' AND ev.event_date < '2027-01-01' (the average cart is the average of class 'TO', tax and shipping included - never of 'ST'. The accounting weight applies to the DENOMINATOR too: SUM(ev.sign) nets a refunded order out of the order count exactly as its amount is deducted from the numerator)
- 'amount refunded' / 'refunded amount in 2026' / 'how much was refunded' / plan metric refunded_amount → SELECT ROUND(SUM(ev.amount), 2) AS refunded_amount FROM (SELECT (SELECT MIN(h.date_added) FROM {{table_prefix}}orders_status_history h WHERE h.orders_id = o.orders_id AND h.orders_status_id = o.orders_status) AS event_date, (SELECT SUM(CASE WHEN ot.class = 'TO' THEN ot.value ELSE -ot.value END) FROM {{table_prefix}}orders_total ot WHERE ot.orders_id = o.orders_id AND ot.class IN ('TO','TX','SH')) AS amount FROM {{table_prefix}}orders o JOIN {{table_prefix}}orders_status os ON os.orders_status_id = o.orders_status AND os.language_id = {{language_id}} WHERE os.revenue_sign = -1) ev WHERE ev.event_date >= '2026-01-01' AND ev.event_date < '2027-01-01' - the deduction leg ALONE, as a positive amount, dated on the day the order ENTERED the refunded status: never add the sale leg, which nets a refunded order to 0 and answers revenue instead.
- 'average purchase per customer' / 'revenue per customer' / 'average spend per customer in 2026' / plan metric revenue_per_customer → SELECT ROUND(SUM(ev.sign * ev.amount), 2) AS revenue_ht, COUNT(DISTINCT CASE WHEN ev.sign = 1 THEN ev.customers_id END) AS customers_count, ROUND(SUM(ev.sign * ev.amount) / NULLIF(COUNT(DISTINCT CASE WHEN ev.sign = 1 THEN ev.customers_id END), 0), 2) AS revenue_per_customer FROM ({{event_axis_order_customer}}) ev WHERE ev.event_date >= '2026-01-01' AND ev.event_date < '2027-01-01' - ONE figure: merchandise revenue divided by the number of DISTINCT customers who bought in the window, with revenue_ht and customers_count selected beside it. It is not the average cart, and it is not broken down by customer unless the plan names customer as a dimension.
- 'gross margin in 2026' / 'margin by period' / 'what is my margin' → SELECT ROUND(SUM(ev.sign * ev.line_revenue), 2) AS line_revenue, ROUND(SUM(ev.sign * ev.line_cost), 2) AS cost_ht, ROUND(SUM(ev.sign * (ev.line_revenue - ev.line_cost)), 2) AS gross_margin_amount, ROUND(SUM(ev.sign * (ev.line_revenue - ev.line_cost)) / NULLIF(GREATEST(SUM(CASE WHEN ev.line_cost IS NOT NULL THEN ev.sign * ev.line_revenue END), 0), 0) * 100, 2) AS gross_margin_pct, ROUND(SUM(CASE WHEN ev.line_cost IS NULL THEN ev.sign * ev.line_revenue END), 2) AS revenue_without_cost FROM ({{event_axis_line_cost}}) ev WHERE ev.event_date >= '2026-01-01' AND ev.event_date < '2027-01-01' (the cost basis is the one FROZEN on the order line at sale, op.products_unit_cost; a line written before it was recorded falls back to products_cost + products_handling of the CURRENT catalogue, so such a line whose product was deleted since carries NO cost and is left out of the margin. revenue_without_cost is the revenue they carry - ALWAYS state it in the answer with its share of line_revenue, it is how much of the sales the margin does not cover)
- 'discounts granted to customers' → SELECT o.customers_id, MAX(o.customers_name) AS customers_name, ot.orders_id, ot.title, ot.value AS discount FROM {{table_prefix}}orders o JOIN {{table_prefix}}orders_total ot ON o.orders_id = ot.orders_id AND ot.class = 'CD' JOIN {{table_prefix}}orders_status os ON os.orders_status_id = o.orders_status AND os.language_id = {{language_id}} WHERE os.revenue_sign <> 0 GROUP BY o.customers_id, ot.orders_id, ot.title, ot.value ORDER BY o.customers_id

MULTI-PERIOD TEMPORAL QUERIES (one row per period - day, week, month, quarter, year):

When a query asks for a metric across SEVERAL periods (e.g. "in 2025 and 2026", "per quarter", "by month this year", "per day last week"), return ONE ROW PER PERIOD using GROUP BY on the period expression. NEVER chain contradictory single-date conditions for different periods (e.g. do not write "date >= X AND date = Y").

Pick the GROUP BY expression by granularity (keep it in SELECT aliased, and ORDER BY it). For an AMOUNT metric, `date` below is ev.event_date of the event axis, never o.date_purchased:
- by year: GROUP BY YEAR(date)
- by quarter: GROUP BY YEAR(date), QUARTER(date)
- by month: GROUP BY YEAR(date), MONTH(date)
- by week: GROUP BY YEARWEEK(date, 1)
- by day: GROUP BY DATE(date)
YEAR/QUARTER/MONTH are allowed HERE, as the GROUP BY expression. They remain FORBIDDEN as the period FILTER: the window is always an explicit range.
Use the aggregate that matches the wording: AVG for "average", SUM for "total"/"turnover"/"revenue", COUNT for "how many".

YEAR-OVER-YEAR COMPARISON (relative years like "this year" vs "last year"):
"This year" is a PARTIAL current period: it stops today. A whole previous year is therefore NOT comparable with it. Compare two windows of the SAME length — build the previous one by shifting the current one back with INTERVAL 1 YEAR — and return them as two labelled columns with CASE WHEN (rule 13). Each column spells BOTH of its own bounds — never rely on the outer WHERE to close a window, a half-open CASE silently returns 0. Do NOT put both years in one range and GROUP BY YEAR: that puts a full previous year face to face with a partial current one, and every variation is then wrong in the direction that reassures. An amount or a count varies in percent, a rate varies in percentage points.
- 'compare revenue this year and last year' / 'revenue this year vs last year' → SELECT SUM(CASE WHEN ev.event_date >= MAKEDATE(YEAR(CURDATE()), 1) AND ev.event_date < CURDATE() + INTERVAL 1 DAY THEN ev.sign * ev.amount ELSE 0 END) AS current_revenue, SUM(CASE WHEN ev.event_date >= MAKEDATE(YEAR(CURDATE()), 1) - INTERVAL 1 YEAR AND ev.event_date < CURDATE() + INTERVAL 1 DAY - INTERVAL 1 YEAR THEN ev.sign * ev.amount ELSE 0 END) AS previous_revenue FROM ({{event_axis_order_amount}}) ev

- 'compare sales year by year, by quarter' / 'comparaison annuelle par trimestre' → WITH ev AS ({{event_axis_order_amount}}), q AS (SELECT YEAR(ev.event_date) AS period_year, QUARTER(ev.event_date) AS period_quarter, SUM(ev.sign * ev.amount) AS revenue FROM ev GROUP BY YEAR(ev.event_date), QUARTER(ev.event_date)) SELECT c.period_year, c.period_quarter, c.revenue, p.revenue AS same_quarter_last_year, ROUND((c.revenue - p.revenue) / NULLIF(p.revenue, 0) * 100, 2) AS variation_percent FROM q c LEFT JOIN q p ON p.period_year = c.period_year - 1 AND p.period_quarter = c.period_quarter ORDER BY c.period_year, c.period_quarter
NEVER pair the two years by RANK with a LAG over the ordered rows: that assumes four rows per year, and a GROUP BY only returns the quarters that HAVE sales - one empty quarter shifts every comparison onto the wrong one. Pair them by the CALENDAR KEY, by joining the aggregate to itself on year - 1 and the same quarter.
The quarter in progress is itself partial: its variation_percent is not final and must be presented as such, never as a closed result.
Whenever the result carries SEVERAL SUCCESSIVE PERIODS, return the variation as its OWN COLUMN beside the measure - never leave it to be read off the rows. Name that column variation_percent for an amount or a count, and variation_points for a rate, which varies in PERCENTAGE POINTS and never in percent. Pair the two periods by their CALENDAR KEY: year - 1 and the same period for a year-over-year reading, the immediately preceding period for a step-by-step one. The first period has no predecessor: its variation is NULL, never 0.
When the comparison is made PERIOD BY PERIOD inside ONE window - revenue by quarter over 3 years, by month over 2 years - the previous-period aggregate covers the SAME window as the current one: NEVER shift it back by a year. The calendar-key join does the pairing on its own, and each period finds its own N-1 inside that window. Shifting it asks for a span the window never covered, the subquery returns no row, and EVERY variation comes back NULL - a column that promises a figure and carries none. The PAIRED WINDOWS convention above governs a comparison of TWO WHOLE WINDOWS, never a per-period breakdown.

- the ACCOUNTING WEIGHT of the order status applies to every one of these sums - revenue, margin, average cart, units sold. It is the column {{table_prefix}}orders_status.revenue_sign, never a status id and never a status name: 1 the order counts as a sale, 0 it never became one and is dropped, -1 the sale was undone and must be DEDUCTED at the date of the status change, never merely excluded. Join it as `JOIN {{table_prefix}}orders_status os ON os.orders_status_id = o.orders_status AND os.language_id = {{language_id}}` and build the sum with the CANONICAL SHAPE of the ORDER STATUS FILTERING section - a UNION ALL over an event date. Writing a status id in a filter is always wrong. That dating is for AMOUNTS summed over a window. A COUNT of orders counts each order ONCE, on its purchase date, and reads its CURRENT weight: orders_count never subtracts its refunds, and when the question defines the orders by when they were PLACED ('orders placed in 2025', 'of last year's orders') the refunded or cancelled ones among them are counted over that same purchase window - an order placed in 2025 and refunded in 2026 is a refunded 2025 order.
- HISTORY DOES NOT DEPEND ON THE CATALOGUE. A product that was ordered can be DELETED from the catalogue later, and its revenue MUST still be counted: the order line records the sale, the catalogue only holds the current offer. So NEVER reach the CATALOGUE with an INNER JOIN to compute an amount - that means {{table_prefix}}products, {{table_prefix}}products_description AND the whole category chain {{table_prefix}}products_to_categories, {{table_prefix}}categories, {{table_prefix}}categories_description: a deleted product carries no category row either, so one INNER JOIN anywhere in that chain throws it out through the back door - a deleted product then vanishes with its whole history, the total shrinks, and there is no warning, no error and no zero row to notice. Use LEFT JOIN and name the product with COALESCE(pd.products_name, op.products_name): {{table_prefix}}orders_products.products_name carries the label FROZEN at order time, which survives deletion, renaming and translation. Always close the description join on AND pd.language_id = {{language_id}} - without it a product carrying two labels comes back twice and its amount is counted twice. Group a product breakdown on op.products_id, NEVER on a name: the frozen label is written in the language the BUYER was browsing, so one product ordered in two languages carries two labels and a GROUP BY on the name splits it into two rows that each look like a separate product.
- the ANALYSIS PLAN names the basis when it carries a revenue metric: revenue_ht = EXCLUDING tax (the 'TO' minus 'TX' form), revenue_ttc = INCLUDING tax (the 'TO' form). Use the form of the metric the plan named, alias the column with that exact name, and never substitute the other basis.
- the ANALYSIS PLAN names the cost basis when it carries a margin metric: gross_margin_amount = SUM(op.final_price * op.products_quantity) - SUM(COALESCE(op.products_unit_cost, p.products_cost + p.products_handling) * op.products_quantity) over the sold lines, gross_margin_percent = that amount / SUM(op.final_price * op.products_quantity) * 100. The cost basis is the one frozen on the order line at sale (op.products_unit_cost); only a line without it reads products_cost PLUS products_handling, joined from {{table_prefix}}products. NEVER emit a margin without subtracting the cost basis (revenue aliased as a margin reads as 100% and is false), and when the plan names the metric use THIS form, never the catalogue-price form, and alias the column with the exact metric name. "Over the sold lines" is the ACCOUNTING WEIGHT and not a figure of speech: build this form INSIDE the canonical shape of the ORDER STATUS FILTERING section, exactly like a revenue sum - join {{table_prefix}}orders_status, drop what never became a sale, and DEDUCT an undone sale at the date of its status change. A margin summed over raw order lines counts cancelled and refunded orders as profit. A line whose product carries NO cost - products_cost NULL or 0 - has no margin and is LEFT OUT of it: write its cost COALESCE(op.products_unit_cost, NULLIF(p.products_cost, 0) + p.products_handling) * op.products_quantity so it stays NULL, sum the margin denominator over the costed lines only - SUM(CASE WHEN ev.line_cost IS NOT NULL THEN ev.sign * ev.line_revenue END) - and in a breakdown KEEP a group without any costed line, never filter it out: its margins come back NULL and the answer names it; a revenue column in the same query still sums EVERY line. NEVER COALESCE the cost to 0: the gap would read as a 100% margin. gross_margin_percent is a rate over SALES: when the costed net revenue of a row is zero or negative - a period that only holds a refund - the rate is NULL, never a positive figure next to a negative amount, so wrap its denominator as NULLIF(GREATEST(..., 0), 0).
- BOTH MARGIN FIGURES TRAVEL TOGETHER: a query selecting gross_margin_amount ALSO selects gross_margin_percent, and the reverse, at the same level and with the forms above - the amount without its rate, or the rate without its amount, is half an answer. When the result carries a variation, each keeps its own: in percent for the amount, in percentage points for the rate.
- A RANKING ON A MARGIN (the best or worst margins, top or bottom N by gross_margin_amount or gross_margin_percent) ranks only the rows that carry a net sale: add HAVING SUM(ev.sign * ev.line_revenue) <> 0 before the ORDER BY. A row whose sales were all refunded has no margin, not a low one, and ranking it fills one of the N places with nothing to act on.
- MANDATORY COMPANIONS OF ANY MARGIN: whatever the question, its wording, its language, its period, its comparison or its breakdown, a query selecting gross_margin_amount or gross_margin_percent ALSO selects, at the same level, line_revenue over EVERY line = ROUND(SUM(ev.sign * ev.line_revenue), 2), never wrapped in a CASE on the cost - the costed-lines sum is the rate denominator only, never a column: aliased line_revenue it hides the uncovered revenue under a name that promises all of it - and revenue_without_cost = ROUND(SUM(CASE WHEN ev.line_cost IS NULL THEN ev.sign * ev.line_revenue END), 2) - the revenue the margin does not cover, never a count of lines. NEVER drop the lines without cost in the WHERE clause (no ev.line_cost IS NOT NULL): the margin already skips them, and the revenue they carry must stay measurable. These two columns are part of the margin, not an extra metric: the ANALYSIS PLAN never forbids them. Everywhere else they are computed per row, in the same GROUP BY as the margin they accompany: never in a separate CTE joined onto the rows, which would repeat the window's total on every row under a name that promises that row's revenue. ONLY on a DENSE DAY AXIS (the plan's time grain is DAY) are they NOT carried through the days: there, compute them once per window, over the whole window, in their own small CTE, and CROSS JOIN that single row onto the final rows.
- the ANALYSIS PLAN names the form when it carries one of these: discount_amount = SUM(ot.value) with ot.class IN ('CD','DC'), shipping_billed = SUM(ot.value) with ot.class = 'SH'. Both are order-grain sums; alias the column with the exact metric name. NEVER fold discount_amount into a revenue or a margin metric - return it as its own column, never subtracted from them and never added back.

GROUP BY it and select it RAW (0 or 1, never a label, never renamed) aliased tax_convention, next to the metric. text_sql_domain_grain_classes = WHICH orders_total CLASS NAMES WHICH QUANTITY: 'ST' is the products sub-total, 'SH' the shipping, 'TO' the grand total actually paid by the customer. The AVERAGE CART is the average of 'TO', never of 'ST'. Product revenue is NOT built on 'ST' either: 'ST' is written in the tax convention of EACH order, so summing it adds tax-inclusive amounts to tax-exclusive ones. Order revenue comes from 'TO' as stated in the class map above; the revenue of a PRODUCT line comes from {{table_prefix}}orders_products, never from orders_total. Never sum two different classes together, and never assume a class exists on every order.
SHARE OF ONE CLASS IN THE TOTAL - shipping weight, discount weight, fee weight: NAME the denominator, because the two revenues differ by the whole tax AND the shipping, and the same ratio moves by a fifth on a 20 percent shop. Revenue INCLUDING tax = SUM(ot.value) with ot.class = 'TO' (invoiced, shipping included). MERCHANDISE revenue = SUM(CASE WHEN ot.class = 'TO' THEN ot.value ELSE -ot.value END) with ot.class IN ('TO','TX','SH'). A SHIPPING-weight ratio takes the INVOICED total as denominator: shipping is not part of the merchandise revenue. Say in the answer which one the ratio uses.
FORBIDDEN: SELECT SUM(sh.value) / SUM(tot.value) FROM {{table_prefix}}orders o JOIN {{table_prefix}}orders_total sh ON sh.orders_id = o.orders_id AND sh.class = 'SH' JOIN {{table_prefix}}orders_total tot ON tot.orders_id = o.orders_id AND tot.class = 'TO'
MANDATORY: SELECT ROUND(SUM(CASE WHEN ot.class = 'SH' THEN ot.value ELSE 0 END) / NULLIF(SUM(CASE WHEN ot.class = 'TO' THEN ot.value ELSE 0 END), 0) * 100, 2) AS shipping_share_pct FROM {{table_prefix}}orders o JOIN {{table_prefix}}orders_total ot ON ot.orders_id = o.orders_id
SHIPPING IS THE FIRM PRICE CHARGED: 'SH' is the shipping amount actually billed, and it is the ONLY shipping reference. It ALREADY contains packaging and handling - the box weight and the padding inflate the weight sent to the carrier rate table, and the result collapses into this single value. NEVER split 'SH' into transport versus packaging, and never rebuild it from product weights or from shipping configuration constants: that decomposition is stored nowhere, and a shipping module may compute it its own way.
