PLAN FORMAT
{"periods": {"current": {"from": "YYYY-MM-DD", "to": "YYYY-MM-DD"}, "compare": "none|previous_year|previous_year_comparable_days|previous_period", "set_bounded": false}, "metrics": [{"name": "<a name from the list above>"}], "unsupported": ["<a measure the question asks for that the list does not carry>"], "dimensions": ["<what the result is broken down by>"], "rankings": [{"metric": "<a metric you listed>", "direction": "top|bottom", "n": 3, "partition_by": "<dimension or null>"}], "filters": {}, "act": false, "complexity": 1}
RULES
1. metrics: use ONLY names from the list above - never invent a name, never approximate with a neighbour.
1bis. unsupported: when the question asks for a measure the list does not carry, keep it OUT of metrics and name it there, in the words of the question. It is how the answer tells the user what it could not serve; an omission it cannot name is an amputation. Leave it empty when the question asks for no measure at all - a stock level, a price, a list - that is not an unsupported measure. Never name there the ACT the question asks for - a strategy, a plan, a recommendation: the act is served by the answer that follows, not by this plan, and declaring it makes the answer deny what it is about to deliver. Never name there the DIRECTION of a measure the list DOES carry - declining, falling, rising, dropping: the direction is read from that measure over the window, it is not a measure of its own.
1ter. metrics: a question that asks for RECORDS is not a metric aggregation - "the last N records of an entity", "list the members of an entity", one item's price, a stock level. Return metrics EMPTY for it, and the question is handled without a plan. Proposing a metric there costs twice: it replaces the records with a count, and it forces a window the question never asked for - and the plan is BINDING, so that invented window becomes law and the answer comes back empty. The words "the last N" alone do not make it a records question: when the question asks for a MEASURE computed over those N - the revenue of the last 5 orders, the total of the last 3, the margin of the last 10 - it IS a metric aggregation, elect the metric and leave periods.current null, the N bounds the set on its own, and set periods.set_bounded true so that stays true. That flag is the ONLY thing that separates a set the question already bounds from a question carrying no period at all: without it a default window is applied to both, and the plan being BINDING, it becomes law. Set it true ONLY when something other than time already bounds the measured set; leave it false whenever the question simply names no period. What makes it records is that the question asks for no measure at all.
2. periods.current: the window the question actually asks about, as concrete YYYY-MM-DD bounds. Never widen it, never narrow it. It is the window the question CARRIES. A RELATIVE period the question states IS a carried window - last quarter, last month, last year, the past 30 days - resolve it to concrete bounds against TODAY (last quarter = the whole calendar quarter before the one TODAY falls in; last month = the whole previous calendar month; last year = the whole previous calendar year). The quarter, month or year TODAY falls in is THIS one, never the last one, even while it is not over and whatever the tense of the question: "what is X for the last quarter" names the quarter BEFORE the one TODAY falls in, never the quarter in progress. Leave current null ONLY when NEITHER the question NOR the WIDER REQUEST it was cut from carries any period: never default to today and never invent one.
2bis. periods.current, when the question is one PART of the WIDER REQUEST shown below it: the scope stated once governs every part. When this question states no period of its own and the wider request states one, resolve the wider request's period and use it here - it was already given, so asking for it again is a refusal to answer a question that was complete. A part naming a comparison without a base window - "compared with the same period of the previous year" - IS this case: take the base window from the wider request. When the wider request is blank, or carries no period either, rule 2 applies unchanged and current stays null.
2ter. periods.current, a span of SEVERAL units - the last 3 years, the last 6 months, the last 4 quarters: this is a ROLLING window ENDING TODAY, not a run of whole calendar units. The last 3 years starts three years before TODAY and ends TODAY; it INCLUDES the current year. Reading it as the three complete calendar years before this one drops the most recent activity entirely - the very period the question is asking about - and does it silently. The whole-calendar-unit convention of rule 2 belongs to the SINGULAR form alone (last year, last quarter, last month), where the point is precisely to exclude a partial current unit.
3. compare: say WHETHER to compare, never WHAT to compare with. The second window is computed for you. Writing it yourself is how an empty interval gets produced.
3bis. compare, year on year: there are TWO conventions and they are never mixed. previous_year is the CALENDAR one - the same dates one year back - and it is the default whenever the question does not say otherwise. previous_year_comparable_days aligns the DAYS OF WEEK instead - the same window 52 weeks back, hence the same count of Saturdays and business days - and you choose it only when the question asks for comparable days, comparable weeks, equal business days or like-for-like trading days. Never propose both for one measure: they are two different readings, not two halves of one.
4. Do NOT write the grain or the type of a metric: both are already known and will be filled in.
4bis. dimensions: ONLY what the question asks the result to be BROKEN DOWN BY. A word that belongs to the METRIC's own name is NOT a dimension - "product revenue by quarter" is broken down by quarter ALONE, "product" says what the measure counts, not a cut of it. Every dimension you add multiplies the rows and answers a question nobody asked. A measure PER or BY an entity - the margin per order, the revenue by customer - IS a breakdown by that entity, one row each, and never a measure missing from the list: name the entity in dimensions and keep the measure in metrics. Only an AVERAGE per entity the question asks for in those words is a measure of its own. When the question names no breakdown, leave it empty.
5. rankings: one entry per ranking. A top 3 and a bottom 3 are TWO entries. partition_by names the dimension inside which the ranking applies.
6. complexity: 1 to 5, for the audit trail only. It routes nothing.
7. filters: a criterion belongs there ONLY when the question states it as an explicit value the data holds. A QUALITATIVE criterion the question uses without defining it - the low ones, the best ones, the least active - carries neither column nor threshold: written there it travels as a phrase no query can honour, and the selection ends up made silently outside the data. Name it in unsupported instead, in the words of the question, and leave filters empty. Saying the criterion was not applied is worth more than a selection nobody can check.
8. An OBJECTIVE is not served by the measure it names alone. When the question asks to increase, improve or reduce something, elect with that measure the ones its diagnosis needs - taken from the list above, never invented, and at most two more. A question that only asks to READ a measure gets no such company.
9. act: true when the question asks what to DO - a strategy, an action, a recommendation, how to improve, raise or reduce something; false when it only asks to read, list, rank, compare or explain figures. Asking WHY a figure moved is an explanation, not a request for action. It changes nothing else in this plan: it only tells the answer whether to propose actions.
