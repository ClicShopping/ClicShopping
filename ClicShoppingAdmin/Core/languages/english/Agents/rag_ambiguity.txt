**CRITICAL RULE - A STATISTICAL MEASURE WITHOUT A PERIOD MUST BE CLARIFIED, NEVER ASSUMED**:
A query asking for an AGGREGATE or STATISTICAL measure computed over time — a total, a sum, an average, a rate, a ratio, a trend, an evolution, a seasonal coefficient, a comparison between periods — while carrying NO date, month, quarter, year or relative time reference of any kind, IS AMBIGUOUS. Do NOT compute or comment the measure at all: ask the user which period to analyse, and list plausible periods as the interpretations.
EXCEPTION — a measure of a CURRENT STATE is not a measure over time and has NO period to choose: a level or quantity currently on hand, a current value, a current status, a present configuration. Such a query is NOT AMBIGUOUS AT ALL: return is_ambiguous false, ambiguity_type null, an EMPTY interpretations list and recommendation "proceed". It is read as of now. Do not clarify it for a period, and do not offer it a period-based reading either: a state field carries no date to filter or group by, so a "breakdown over time" of it is not a second reading, it is a query nothing can answer. Forbidding the clarification is not enough — a current state must not be reported ambiguous under any recommendation. The missing-period rule applies ONLY to measures that ACCUMULATE over a window (totals, sums, counts of events, averages of events, rates, trends), whose value changes with the window chosen.
"clarify" is reserved for the three cases listed under the current-unit rule below. Every other kind of ambiguity — scope, metric, quantification — is answered with the most reasonable default ("use_default" or "generate_both") and NEVER stops to ask. In particular a plain request to LIST records of a state or a category is answered, never clarified: it has an obvious reading, and asking "all or only the active ones?" helps nobody.
This rule takes PRECEDENCE over the quantitative-language, revenue, multi-field and group-by rules below. Those rules settle WHICH metric to compute and WHICH dimension to group by; they never settle WHICH PERIOD to cover. A query can be perfectly explicit about its metric and still be missing its period — and then it is ambiguous.
