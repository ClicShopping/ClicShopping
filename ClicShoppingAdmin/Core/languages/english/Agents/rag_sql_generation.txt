13. TEMPORAL COMPARISONS: When comparing metrics between periods (e.g., "may vs february", "this year vs the same period last year"):
- Use CASE WHEN with SUM() to create separate columns, one per window, labelled current_ / previous_
- Example: SUM(CASE WHEN date >= '2026-05-01' AND date < '2026-06-01' THEN value ELSE 0 END) AS may_value
- PAIRED WINDOWS (MANDATORY): the two windows MUST cover the SAME number of days. Build the previous one by shifting the current one back with INTERVAL 1 YEAR (or INTERVAL 1 MONTH). Comparing a partial current period with a whole previous one makes every variation wrong, and wrong in the direction that reassures.
- Each CASE spells BOTH bounds of its own window, as an explicit date range
- Return results in single row with multiple columns
- VARIATION DEPENDS ON THE TYPE OF METRIC: an AMOUNT, a COUNT or a DURATION varies in percent — (current - previous) / previous * 100. A RATE (a percentage, a share, a conversion rate) varies in PERCENTAGE POINTS — current_rate - previous_rate. A rate going from 70% to 72.73% is +2.73 percentage points, never "+3.9%": dividing one rate by another is a category error, and it is undetectable once printed in a table.
14. DYNAMIC TIME EXPRESSIONS: a period FILTER is ALWAYS an explicit range on the raw date column - never YEAR(), MONTH() or QUARTER() in a WHERE. Take the bounds from the ANALYSIS PLAN, else from the CURRENT DATE CONTEXT block. A range built from the first day of a period crosses the year boundary by construction.
- "Last 30 days" → WHERE {{domain_date_column}} >= CURDATE() - INTERVAL 30 DAY
- "This week" → WHERE {{domain_date_column}} >= CURDATE() - INTERVAL WEEKDAY(CURDATE()) DAY AND {{domain_date_column}} < CURDATE() + INTERVAL 1 DAY
- "Last month" → WHERE {{domain_date_column}} >= DATE_FORMAT(CURDATE() - INTERVAL 1 MONTH, '%Y-%m-01') AND {{domain_date_column}} < DATE_FORMAT(CURDATE(), '%Y-%m-01')
- "This month" → WHERE {{domain_date_column}} >= DATE_FORMAT(CURDATE(), '%Y-%m-01') AND {{domain_date_column}} < CURDATE() + INTERVAL 1 DAY
- "Last quarter" → WHERE {{domain_date_column}} >= MAKEDATE(YEAR(CURDATE()), 1) + INTERVAL (QUARTER(CURDATE()) - 2) * 3 MONTH AND {{domain_date_column}} < MAKEDATE(YEAR(CURDATE()), 1) + INTERVAL (QUARTER(CURDATE()) - 1) * 3 MONTH (asked in January 2026, this is October 1 to December 31, 2025)

text_sql_rules_grain = GRAIN - HEADER-LEVEL VALUES OVER A LINE JOIN
A JOIN from a header table to one of its line tables, or through a many-to-many link, turns one header into ONE ROW PER LINE. Every header-level value on those rows - an amount, a date - is REPEATED once per line.
{{domain_grain_tables}}
The trap is not a missing GROUP BY, it is SUM over a repeated value. Inside a GROUP BY on the header id that also joins a line table, SUM over a header value multiplies it by the number of lines. Take a repeated header-level value with MAX - one value per header - or keep the line join out of the aggregate and restrict the population with EXISTS.
{{domain_grain_examples}}
This applies to HEADER-level values only. A line-level metric - a quantity, a number of lines, the amount of a line - is aggregated over the line table as usual and must NOT be pre-aggregated to header grain.
SHARE OF ONE PART IN A TOTAL: NEVER inner-join the part you are measuring: a header carrying no row of that part then vanishes from the DENOMINATOR as well, and the ratio comes out overstated. Aggregate both sides in one pass, with conditional sums over a single join.
{{domain_grain_classes}}
